# Client-side search and listing indexes for E2EE apps

**Status:** research complete (October 2026); not implemented. Feeds the
Office home catalog (Phase 1 below) and later Chat and notes search
(Phase 2). Entries in [`../roadmap.md`](../roadmap.md) track the work.

**Method:** four parallel research passes, then a synthesis. Code was read in
the reference clones kept beside this repository (Proton WebClients and
ProtonDriveApps/sdk, Signal-Desktop, element-web, matrix-js-sdk and
matrix-rust-sdk, Ente, CryptPad) and in public repositories (Tuta, Seshat,
Wire, Threema, MEGA, Bitwarden, Standard Notes). Browser storage findings come
from vendor documentation and engineering posts; the Turkish folding and FTS5
size figures come from small local tests with SQLite 3.53.4.

**Why:** the Office home ([`frontend/apps/office`](../../frontend/apps/office))
lists documents by decrypting the metadata of every file in every readable
folder on each visit, which does not scale to large accounts, and search
across apps has no index at all.

## Summary

E2EE products that search well do it the same way. **The index lives only on the device, it is derived from the encrypted server data, it is encrypted at rest under a random key wrapped by the account key, and it is thrown away and rebuilt whenever the format, key or tokenizer changes.** Under that common rule they split in two. Native and Electron clients (Signal Desktop, Tuta desktop and mobile, Threema, Element Desktop) put SQLite or SQLCipher with FTS5 or Tantivy on disk. Browser clients (Proton, Tuta web, Wire, MEGA, Ente, CryptPad, Standard Notes, Bitwarden) use IndexedDB, and nearly all of them still search by scanning decrypted objects in memory. The one browser exception is Proton's 2026 Rust/WASM "Foundation Search" engine, which stores encrypted blobs in IndexedDB. For Kutup's Office home, the recommendation follows from that. Phase 1 is a per-node encrypted **metadata catalog** in the Rust core's existing IndexedDB store, kept current from a server event cursor and decrypted into worker memory once per session. This removes the need to decrypt every file on each visit, and a Turkish-folding linear scan over it gives search at no extra cost. Phase 2, when chat and notes content needs real full-text search, is **one Rust SQLite FTS5 index** shared by native and web: rusqlite with SQLCipher natively, `sqlite-wasm-rs` on OPFS in a dedicated worker on the web. It uses a custom tokenizer that folds İ/I/ı/i to `i`, because no engine does this correctly by default. The open risks are encryption at rest for SQLite in the browser, multi-tab ownership of OPFS, and Safari's eviction rules. All three are manageable if the index is treated as disposable.

## Most E2EE clients still decrypt everything and scan it in memory

Products choose one of three local designs, and the choice decides what you pay on each visit. The first design persists only the server's ciphertext and decrypts it into memory on every load. Bitwarden keeps encrypted ciphers on disk and decrypted ones only in memory. Its lunr index is never persisted, because the code says that would "eats significantly more memory" ([bitwarden/clients](https://github.com/bitwarden/clients/blob/main/libs/common/src/vault/services/lunr-search.service.ts)). Standard Notes re-encrypts payloads before writing them to IndexedDB ([standardnotes/app](https://github.com/standardnotes/app/blob/main/packages/snjs/lib/Services/Storage/DiskStorageService.ts)). CryptPad caches encrypted channel logs and rebuilds its drive object in a SharedWorker. It then searches with a linear `toLowerCase().indexOf()` over every title ([cryptpad](https://github.com/cryptpad/cryptpad/blob/main/src/common/user-object.js)). The second design persists an **encrypted local index**: Proton's new Drive search, Proton Mail's encrypted search, Tuta web and MEGA. The third persists **decrypted metadata in plaintext**. Ente does this, storing every file's decrypted metadata *and its file key* in one IndexedDB value under the key `"files"` ([ente](https://github.com/ente-io/ente/blob/main/web/packages/new/photos/services/photos-fdb.ts)). On mobile it uses a plain SQLite `title` column with no SQLCipher ([ente](https://github.com/ente-io/ente/tree/main/mobile/apps/photos/lib/db)).

| Product | Local engine | Index encrypted at rest? | Search technique |
|---|---|---|---|
| Proton Drive web (2026) | IndexedDB blobs + Rust/WASM engine in a SharedWorker | Yes: AES-GCM-256 per blob, key wrapped by account key | Tokenized inverted index, metadata only, 50k cap |
| Proton Mail v1 / v2 | IndexedDB (`idb`) | Yes: AES-GCM per item (v1) / per blob (v2) | Substring scan over a cache of up to 600 MB (v1); inverted + fuzzy (v2) |
| Tuta web / native | IndexedDB / SQLCipher + FTS5 | Deterministic term encryption (web); whole-DB SQLCipher (native) | Encrypted whole-word inverted index; FTS5 prefix |
| Signal Desktop | SQLCipher + FTS5, Signal tokenizer | Whole DB, key in OS keychain | FTS5 `"tok"*` prefix queries |
| Element Desktop / Element X | Seshat (SQLCipher + Tantivy 0.12) / matrix-sdk-search (Tantivy 0.26) | AES-CTR+HMAC encrypted directory | BM25; optional 2–4 n-grams for CJK |
| Element Web (browser) | none | n/a | No search in encrypted rooms |
| MEGA web | Dexie IndexedDB | AES-**ECB** "obfuscation" | Paged decrypt + in-memory filter |
| Ente web / mobile | localForage IndexedDB / SQLite + usearch | No | Regex scan; brute-force or ANN CLIP |
| Bitwarden, Standard Notes, CryptPad | IndexedDB / disk of server ciphertext | Ciphertext only | In-memory scan / lunr |
| Wire / Threema | Dexie IndexedDB / SQLCipher | Partial / whole DB | Regex per conversation / SQL `LIKE` |

Name search in almost all of these is a linear scan, and it works because metadata is small. Ente's web search worker filters the whole in-memory file list with a regex ([ente](https://github.com/ente-io/ente/blob/main/web/packages/new/photos/services/search/worker.ts)). MEGA pages its node table in chunks of 16,384 rows, decrypts them and filters in memory ([meganz/webclient](https://github.com/meganz/webclient/blob/master/js/mDB.js)). Tresorit searches only names and extensions and sends users to OS search for contents ([Tresorit support](https://support.tresorit.com/hc/en-us/articles/360021137054-Search-in-Tresorit)). Even Proton Drive's web *browsing* keeps no persistent cache. Its SDK runs with `MemoryCache` for entities and crypto, so folder listings are decrypted again each session ([WebClients](https://github.com/ProtonMail/WebClients/blob/main/packages/drive/index.ts)). Its native SDKs ship `SQLiteCache` and an `EncryptedSQLiteCache` (HKDF-SHA256 + AES-256-GCM per value) ([ProtonDriveApps/sdk](https://github.com/ProtonDriveApps/sdk/tree/main/cli/src/cache)). This matters for Kutup. "Listing documents across all folders without decrypting every file" is a *catalog* problem, not a full-text problem, and every product that solves it persists per-node metadata and refreshes it from a change feed.

Note-taking and productivity apps outside E2EE confirm the pattern and its failure modes. Linear keeps its data in IndexedDB and hydrates it into an in-memory MobX graph using server-ordered sync IDs ([reverse-linear-sync-engine](https://github.com/Aslam97/reverse-linear-sync-engine)). Notion moved to official SQLite WASM on the `opfs-sahpool` VFS and measured navigation about 20% faster, and 33% faster in India ([Notion](https://www.notion.com/blog/how-we-sped-up-notion-in-the-browser-with-wasm-sqlite)). Obsidian rebuilds an IndexedDB metadata cache from files. Its users report 280 ms renderer stalls in a vault of about 10.5k files ([forum](https://forum.obsidian.md/t/performance-280-ms-renderer-stall-every-2-seconds-in-large-vault-caused-by-getallpropertyinfos/117693)) and lost IndexedDB writes that force a re-index of more than 25k files on Android ([forum](https://forum.obsidian.md/t/unpractical-vault-load-time-for-large-vaults-on-mobile-indexeddb-transactions-are-not-flushed-to-disk/88470)).

## Proton's 2026 Drive search is the most complete browser design to copy

Proton's new Drive module (`applications/drive/src/app/modules/search/internal/`, about 9.3k lines) is the most complete production design in this set. It is the best template for Kutup's web client, both for what it does right and for the limits it hit. **Storage** is one IndexedDB database per user, `search:<userId>`, holding encrypted `indexBlobs` plus plaintext bookkeeping stores for event cursors, populator state, BFS visitor state and repair entries ([WebClients](https://github.com/ProtonMail/WebClients/tree/main/applications/drive/src/app/modules/search/internal)). **The key** is a random 256-bit AES-GCM key, OpenPGP-encrypted *and signed* with the account key. Each blob is CBOR-serialized and encrypted with AAD `drive.search.blob.{indexKind}.{blobName}`, "so blobs cannot be swapped or replayed across indexes". If unwrapping fails, a new key is generated and the index cleared ([README](https://github.com/ProtonMail/WebClients/blob/main/applications/drive/src/app/modules/search/internal/README.md)). Mail v2 adds a critical signature context, `mail.search.index`. It also re-checks inside a readwrite transaction so that two tabs cannot both create a key ([indexKey.ts](https://github.com/ProtonMail/WebClients/blob/main/applications/mail/src/app/contentSearch/crypto/indexKey.ts)).

**Staying current** combines three mechanisms. The SDK polls events every 30 s in the foreground and every 10 min in the background ([eventScheduler.ts](https://github.com/ProtonDriveApps/sdk/blob/main/client/js/src/internal/events/eventScheduler.ts)). A persisted `latestEventId` per scope lets a reloaded tab resume from its cursor, and a server `TreeRefresh` event marks the index for a rebuild. The initial build is a resumable BFS folder walk that commits every 30 entries and checkpoints every 10 folders. Failed nodes go to a repair queue that is retried every 24 h ([WebClients](https://github.com/ProtonMail/WebClients/tree/main/applications/drive/src/app/modules/search/internal)). Other products use simpler delta mechanisms. Ente uses `sinceTime` diffs per collection with tombstones ([ente](https://github.com/ente-io/ente/blob/main/web/packages/new/photos/services/collection.ts)). MEGA wipes its database if the `_sn` sequence record is missing and writes `_sn` last as a commit marker ([meganz/webclient](https://github.com/meganz/webclient/blob/master/js/mDB.js)). Bitwarden re-downloads everything on each `/sync`, and its users complain about it ([Bitwarden community](https://community.bitwarden.com/t/selective-collection-sync-to-desktop-browser-and-mobile-apps/34316)).

**The limits Proton hit** should set Kutup's expectations. The index is capped at **50,000 documents**, because "commit time grows super-linearly with the number of documents already in the index (measured)". Eviction starts at 115% of the cap and removes the least recent 15%. Decoded blobs in memory are capped at 20 after "a real production WASM allocator-abort crash (~417 blobs / ~500MB)". Background indexing is held to 400 SDK requests per window, against a server limit of roughly 1,000 per 60 s ([config.ts](https://github.com/ProtonMail/WebClients/blob/main/applications/drive/src/app/modules/search/internal/shared/config.ts)). The feature is opt-in, indexes metadata only, and covers My files but not Shared or Trash ([Proton support](https://proton.me/support/drive-web-guide)). Users still complain that the index "is often lost, even when staying logged in" and must be rebuilt on each device ([Proton UserVoice](https://protonmail.uservoice.com/forums/932839-proton-drive/suggestions/50842439-saving-search-index)). No product here uploads an encrypted index snapshot. The closest is Ente, which encrypts each file's ML-derived data with that file's key and uploads it, so a new device can pull it instead of recomputing ([Ente ML](https://ente.com/ml/)).

The encryption choices also rank the alternatives. Tuta web encrypts search terms with a fixed IV so they can serve as IndexedDB keys, and decrypts postings with `aesDecryptUnauthenticated`. That leaks term equality and frequency to anyone with the disk, and lets them tamper with postings ([IndexEncryptionUtils.ts](https://github.com/tutao/tutanota/blob/master/src/applications/common/api/worker/search/IndexEncryptionUtils.ts)). MEGA's code admits its own AES-ECB with a "FIXME: use CBC" ([mDB.js](https://github.com/meganz/webclient/blob/master/js/mDB.js)). Wire leaves its indexed fields in plaintext so range queries work, and uses an all-zero key when none is configured ([storeEngineProvider.ts](https://github.com/wireapp/wire-webapp/blob/master/apps/webapp/src/script/service/storeEngineProvider.ts)). Native clients encrypt the whole database instead. Signal keys SQLCipher with a raw key protected by Electron `safeStorage`, which falls back to a weak `basic_text` backend on some Linux setups ([Server.node.ts](https://github.com/signalapp/Signal-Desktop/blob/main/ts/sql/Server.node.ts)). Seshat falls back to the literal passphrase `"DEFAULT_PASSPHRASE"` when the OS secret store fails ([seshat.ts](https://github.com/element-hq/element-web/blob/develop/apps/desktop/src/seshat.ts)). Server-side searchable encryption is rejected everywhere, for good reason. Leakage-abuse attacks recover queries and plaintext from realistic leakage ([Cash et al., CCS 2015](https://unpaywall.org/10.1145%2F2810103.2813700)), and blind indexes explicitly do not support full-text search ([CipherSweet](https://ciphersweet.paragonie.com/security)).

## Browser storage forces a single owner per origin and a rebuildable cache

Two engine families are production-grade in browsers in 2026. **IndexedDB** works in every context, including private windows. It allows many concurrent connections and reads or writes a key in about 0.1–0.2 ms, but it has no query planner or full-text search ([RxDB benchmark, vendor](https://rxdb.info/articles/localstorage-indexeddb-cookies-opfs-sqlite-wasm.html)). **SQLite WASM on OPFS** is the other. Sync access handles are Baseline since March 2023 but exist **only in dedicated workers** ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle)), and OPFS is missing in Safari and Firefox private browsing ([PowerSync](https://www.powersync.com/blog/sqlite-persistence-on-the-web)). PowerSync reports that OPFS VFSes keep their performance past 1 GB, while IndexedDB-block VFSes degrade above about 100 MB ([PowerSync](https://www.powersync.com/blog/sqlite-persistence-on-the-web)). The official `opfs-sahpool` VFS needs no COOP/COEP headers and is "easily the highest OPFS performance", but it leaves multi-tab coordination to the application ([sqlite.org](https://sqlite.org/wasm/doc/trunk/persistence.md)). A Rust core does not need a second SQLite build. The `sqlite-wasm-rs` crate gives rusqlite a sahpool VFS on OPFS and a relaxed-idb fallback on wasm32-unknown-unknown ([docs.rs](https://docs.rs/sqlite-wasm-rs)). PGlite does not fit: it is single-connection, and Safari's limit of about 252 open sync access handles blocks its OPFS backend ([PGlite](https://pglite.dev/docs/filesystems)).

**Multiple tabs** is where browser designs break. Notion let several tabs write the same OPFS file and corrupted the database, showing "wrong data" and duplicate rows. It now runs one dedicated worker per tab, picks a single active writer through a SharedWorker, and uses Web Locks to detect closed tabs ([Notion](https://www.notion.com/blog/how-we-sped-up-notion-in-the-browser-with-wasm-sqlite)). Proton Drive runs one SharedWorker per user. It guards the engine with `navigator.locks.request('search-engine:<userId>')` and tracks tabs by heartbeat with a 5-minute timeout, so throttled background tabs are not dropped ([ClientCoordinator.ts](https://github.com/ProtonMail/WebClients/blob/main/applications/drive/src/app/modules/search/internal/worker/ClientCoordinator.ts)). PowerSync avoids SharedWorkers entirely, because they cannot open OPFS sync handles, and holds Web Locks to stop tab suspension ([PowerSync](https://www.powersync.com/blog/sqlite-persistence-on-the-web)). Proton Mail v2 instead uses optimistic revision checks, so a concurrent writer causes a conflict rather than corruption ([EncryptedBlobTransaction.ts](https://github.com/ProtonMail/WebClients/blob/main/applications/mail/src/app/contentSearch/crypto/EncryptedBlobTransaction.ts)).

**Kutup's subdomain layout adds a constraint.** IndexedDB, OPFS, Web Locks, BroadcastChannel and SharedWorker are all scoped to the origin, so the Drive, Office and Chat subdomains cannot share one database ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). Under Chrome's storage partitioning, a same-site iframe from a `storage.` subdomain would keep unpartitioned storage ([Privacy Sandbox](https://privacysandbox.google.com/cookies/storage-partitioning)). That route costs a postMessage hop on every query, and its behaviour in Safari and Firefox was not verified. The simpler and safer choice is **one index per app origin**: the Office app indexes only Office documents. **Eviction** removes a whole origin at once under LRU pressure. Safari also deletes script-written storage after 7 days without user interaction unless the app is installed ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)). `navigator.storage.persist()` prompts in Firefox, so Proton requests it only after a user action ([useEncryptedSearch.tsx](https://github.com/ProtonMail/WebClients/blob/main/packages/encrypted-search/lib/useEncryptedSearch.tsx)). Proton also handles databases that report the current version while missing object stores after eviction ([indexedDB.ts](https://github.com/ProtonMail/WebClients/blob/main/packages/encrypted-search/lib/esIDB/indexedDB.ts)). The lesson every vendor reaches is the one to adopt: **the index is a cache**. Version it, detect when it is empty or corrupt, rebuild it with checkpoints, and never treat it as the source of truth.

## Turkish breaks every default tokenizer, so fold before indexing

Case folding is where Kutup's Turkish users would see wrong results, and no engine handles it out of the box. In JavaScript, `'İstanbul'.toLowerCase()` produces `i` plus U+0307, so it does not equal "istanbul". Generic folding maps `I→i` where Turkish needs `ı`, and `ı` survives NFD mark-stripping ([CaseFolding background](https://unicodefyi.com/glossary/case-folding/)). Local tests with SQLite 3.53.4 and `unicode61 remove_diacritics 2` showed the result in practice. FTS5 folds İ→i and strips ç/ğ/ş/ü/ö, but treats ı as a separate letter, so `isparta` misses "ısparta" and `cagri` misses "Çağrı". The FTS5 tokenizer options are documented at [sqlite.org/fts5](https://sqlite.org/fts5.html). JS libraries fare no better. MiniSearch's default `processTerm` is plain `toLowerCase` ([MiniSearch.ts](https://raw.githubusercontent.com/lucaong/minisearch/master/src/MiniSearch.ts)). Lunr's trimmer uses ASCII `\W` and warns that it "may not work correctly for non latin characters" ([lunr](https://raw.githubusercontent.com/olivernn/lunr.js/master/lib/trimmer.js)). Tantivy's `LowerCaser` is not locale-aware ([lower_caser.rs](https://raw.githubusercontent.com/quickwit-oss/tantivy/main/src/tokenizer/lower_caser.rs)). Only Fuse.js 7.3+ maps ı→i after NFD ([Fuse diacritics.ts](https://raw.githubusercontent.com/krisk/Fuse/main/src/helpers/diacritics.ts)), and Orama ships a Turkish tokenizer and stemmer ([Orama](https://docs.orama.com/open-source/supported-languages)). Lucene's dedicated `TurkishLowerCaseFilter` shows that the problem is well known ([Lucene](https://lucene.apache.org/core/7_4_0/analyzers-common/org/apache/lucene/analysis/tr/TurkishLowerCaseFilter.html)).

The fix is **one Rust fold function applied to both documents and queries**, independent of locale. Apply NFKC. Map İ, I and ı to `i`. Lowercase with plain Unicode rules. Apply NFD and drop combining marks. Then apply a table for letters that do not decompose (ß→ss, ł→l, ø→o; Fuse's table is a ready reference). With this, "İSTANBUL", "Istanbul" and "ıstanbul" all become `istanbul`, and "ÇAĞRI" equals "cagri". English is unaffected. The cost is that Turkish minimal pairs such as kısa and kisa merge. That is a feature for users typing on English keyboards, a problem Turkish IR research addresses as "deASCIIfication" ([Anadolu Univ.](https://earsiv.anadolu.edu.tr/xmlui/handle/11421/19829)). Locale-aware lowercasing (`toLocaleLowerCase('tr')`, ICU4X with a `tr` locale) is the wrong tool. It is only correct when every document is known to be Turkish, and per-user locale would build incompatible indexes. ICU4X `icu_casemap` 2.3 offers `fold_turkic` if a library fold is wanted ([docs.rs](https://docs.rs/icu_casemap/latest/icu_casemap/struct.CaseMapper.html)). Turkish is agglutinative ("İstanbul'dan"), so skip stemming at first. Use prefix queries (`"tok"*`), which Signal and Tuta also use ([Server.node.ts](https://github.com/signalapp/Signal-Desktop/blob/main/ts/sql/Server.node.ts)), and treat the apostrophe as a separator. File names need their own tokens. In local tests unicode61 split `_`, `-` and `.` but not camelCase, and a trigram tokenizer matched inside words. Local benchmarks of 100k short documents measured about **21 MB as a word index, 29 MB with `prefix='2 3'`, and 45 MB as trigram**, with roughly 12–24 ms per 1,000 inserts natively. Run trigram only over file names, which are short. Enable FTS5 `secure-delete=1` so that deleted chat text does not survive in index pages ([sqlite.org/fts5](https://sqlite.org/fts5.html)). Signal's history is a warning: tokenizer changes forced full `rebuild` migrations twice ([migration 1750](https://github.com/signalapp/Signal-Desktop/blob/main/ts/sql/migrations/1750-fts-url.std.ts), [1780](https://github.com/signalapp/Signal-Desktop/blob/main/ts/sql/migrations/1780-fts-reindex.std.ts)). Version the tokenizer and expect to reindex.

## Kutup today, and the server piece Phase 1 needs

- **Listing.** Drive's API lists one folder at a time (`GET
  /api/collections/:id/files`), each response the folder's full contents; the
  Office home and Maps call it for every readable folder and decrypt each
  row. There is no account-wide "what changed since cursor X" feed.
- **Phase 1 therefore needs a server change feed**, one of:
  - *an account change log* (the robust option): a monotonically increasing
    sequence per account covering its own folders, folders shared with it
    and files shared by themselves, recording creates, renames (new sealed
    metadata), moves, re-keys, trash and deletes; the client keeps its
    cursor per account and asks for everything after it, with a "start
    over" answer when the cursor is too old. Comparable to Proton's event
    loop and Ente's per-collection `sinceTime` diffs. The server learns
    nothing new: it already knows these events.
  - *a cheaper first step*: a per-folder revision that changes whenever
    anything in the folder changes, returned in the folder list, so the
    client re-lists only folders whose revision moved. To be checked:
    whether today's `updated_at` on a collection already moves when a file
    in it changes.
- **Storage.** The web Chat core keeps its store in IndexedDB through the
  Rust core; native uses SQLite (with a `sqlcipher` feature). Phase 1 can use
  the same IndexedDB approach in the Office origin without SQLite in the
  browser.
- **One index per app origin.** Office, Drive and Chat live on separate
  subdomains, so each keeps its own catalog of what it shows.

## Open questions before Phase 2

- Does `sqlite-wasm-rs` build with FTS5 enabled? (The official sqlite3.wasm
  build does.)
- How is a browser SQLite database encrypted at rest: an encrypting VFS layer
  (AES-GCM per page, page number as associated data) or Proton's model of
  encrypted blobs around an engine that loads and saves them?
- How do OPFS handles behave in suspended Chrome tabs and Chrome Incognito,
  and does a same-site `storage.` iframe keep unpartitioned storage in Safari
  and Firefox?
- Does folding beat stemming for Turkish recall on Kutup's own data? No
  published comparison exists.

## What Kutup should build, and what each choice costs

**Phase 1, the Office home catalog (build now).** In the Rust core, keep a catalog with one record per node. Fields: node id, parent id, decrypted name and path, Office type, mtime, size, owner and share flags, and a thumbnail reference. Store records in the existing IndexedDB store on the web and in SQLite on native. Each record is AES-GCM-encrypted under a random index key wrapped by the account key, with AAD that binds the record to its node id, as Proton does. Unlike Ente's single `"files"` array, use one record per node, so each delta writes only what changed. Keep the catalog current with a persisted server event cursor per volume or share, plus a resumable, checkpointed folder walk for the first build and for rebuilds after a server "refresh". On open, the worker decrypts the whole catalog into memory once. Sorting by recent, filtering by type, and Turkish-folded name search are then in-memory operations, the same approach Ente, CryptPad and MEGA use for name search. The trade-off is that sorting cannot use IndexedDB's own indexes, because those would require plaintext mtime or type columns on disk, a leak Wire accepts and Kutup should not. Memory sets the limit. Proton's v1 cache budget was 600 MB for about 50k emails with full bodies ([constants.ts](https://github.com/ProtonMail/WebClients/blob/main/packages/encrypted-search/lib/constants.ts)), and metadata-only records are far smaller, so Office libraries in the tens of thousands fit comfortably. That is an inference, not a measurement. For multi-tab, keep IndexedDB, which tolerates many connections, and add a Web Lock so that only one tab syncs from the event cursor and others are told through BroadcastChannel.

**Phase 2, full-text search for Chat and notes (when needed).** Compile SQLite FTS5 into the Rust core with the fold tokenizer above. Natively, use rusqlite with SQLCipher; `kutup-chat-core` already exposes a `sqlcipher` feature in [`crates/kutup-chat-core/Cargo.toml`](../../crates/kutup-chat-core/Cargo.toml). On the web, use `sqlite-wasm-rs` with sahpool on OPFS in a dedicated worker. Elect a Web Lock leader and have other tabs forward queries to it. Fall back to the relaxed-idb VFS or in-memory storage in private windows. This gives one code path, one tokenizer and page-level storage with no need to re-serialize the whole index, which in-memory JS libraries require. The downsides are a WASM SQLite cold start of about 0.5 s in one vendor benchmark ([RxDB](https://rxdb.info/articles/localstorage-indexeddb-cookies-opfs-sqlite-wasm.html)), and suspended Chrome tabs dropping OPFS handles ([PowerSync](https://www.powersync.com/blog/sqlite-persistence-on-the-web)). The largest **unresolved gap** is encryption at rest for that web database. SQLCipher-in-WASM support in `sqlite-wasm-rs` was not confirmed. The realistic options are an encrypting VFS layer that AES-GCMs each page, with the page number as AAD, or Proton's model of encrypted blobs in IndexedDB around an engine that emits load and save events. The notes also do not confirm that `sqlite-wasm-rs` enables FTS5; the official sqlite3.wasm build does ([GNUmakefile](https://raw.githubusercontent.com/sqlite/sqlite/master/ext/wasm/GNUmakefile)). Verify both before committing.

**Alternatives and why they rank lower.** A JS library such as MiniSearch, FlexSearch or Orama inside an encrypted IndexedDB blob is the Skiff approach ([third-party wiki](https://www.mintlify.com/skiff-org/skiff-apps/cryptography/private-search)). It is quick to ship, but it must re-serialize and re-encrypt the whole index on each persist, and every default tokenizer would need the Turkish fold patched in. Tantivy offers better ranking and a Turkish stemmer, and matrix-rust-sdk proves it works natively with an encrypted directory ([matrix-sdk-search](https://github.com/matrix-org/matrix-rust-sdk/blob/main/crates/matrix-sdk-search/Cargo.toml)). It has no browser persistence, though, and Seshat warns that it "doesn't behave nicely if `commit()` is called too often" ([seshat](https://github.com/matrix-org/seshat/blob/master/src/index/mod.rs)). A shared `storage.` iframe would avoid duplicate indexes across subdomains, at the cost of cross-frame latency and quota and partitioning behaviour that was not verified. **Searching inside Office documents** means decrypting and extracting text from every docx, xlsx and pptx. Proton and Tresorit both avoid this, and Proton users still ask for it ([UserVoice](https://protonmail.uservoice.com/forums/945460-general-ideas/suggestions/49554038-proton-drive-full-text-search)). Defer it, and if built, index on native first and limit it to recently opened files. Whatever ships, budget for a full rebuild after eviction: request `persist()` after real engagement, show a "partial index" notice as Proton does, and consider Ente's per-item pattern of uploading derived data encrypted under each item's key, so that new devices do not re-crawl.

## Conclusion

The research reframes Kutup's question. The Office home does not need a search engine. It needs an **encrypted, event-cursor-driven metadata catalog**, and that catalog makes basic search nearly free. The expensive parts are full-text indexing, OPFS ownership across tabs, and encrypting SQLite in the browser. These matter only once Chat and notes content must be searchable. By then, the decisive advantage of a Rust core is that one FTS5 schema and one Turkish fold tokenizer can run unchanged on native SQLCipher and on web OPFS. Proton built a closed-source WASM engine to get the same property, and still hit a 50k-document ceiling and allocator crashes.

The less obvious takeaway is that the correctness bugs users will notice are linguistic and operational, not cryptographic. "ISPARTA" failing to find "ısparta" and an index silently lost after a Safari week are those bugs. Kutup should build its fold function and its "rebuild from cursor" path first and test both against real Turkish data. No vendor has published a recall comparison of folding against stemming for Turkish, so Kutup will have to measure it on its own data.
